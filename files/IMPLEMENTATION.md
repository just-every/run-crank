# Implementation and scope

The browser data service now supplies the existing RER portability importer with a migration replay provider. All placement, additive-column/default checks, staged validation, safety normalization, erasure fencing and atomic publication remain in the installed RER module.

The RER replayer uses Node SQLite. A Vite build plugin invokes that exact replayer against destination-owned migration files while bundling and embeds the resulting schema identities and original statements. The build also obtains migration-seeded row images through the shared replayer, so the importer can distinguish initialization rows from a populated destination. The Worker adapter reads the destination's native migration ledger through the existing RER ledger helpers, resolves file hashes/names, and serves those verified replay identities. Unknown history or a history without a verified snapshot fails closed. No archive SQL is executed. Replay evidence is cached under the ignored .cache directory by all migration SQL/hashes, policy, generator source, RER version and SQLite runtime. The cache is not committed. A typed, inert source placeholder lets existing standalone registry/documentation bundles resolve ordinary source imports. The Worker plugin replaces it with replay evidence; invoking restore without that evidence fails closed.

The harness uses the same replay-module generator and records applied migrations in a native D1 ledger. Its test-only extraMigrations option compiles and applies synthetic SQL without adding a product migration. Existing specialized test bundles keep their original provider/persistence fault plugins and now also resolve the virtual module.

The existing tests/crank.test.mjs BASE-003 DATA-001 registration is unchanged. Its restore journey adds one folded migration-compatibility scenario:

- A real archive exported at main's current migration level restores through the browser POST door into a test build with an added defaulted column and new table. The response is 200/complete, existing records survive, the column takes its default, the new table retains its migration-seeded default record and execution remains inactive.
- A real export from that newer build is refused by a main-level destination, and an original archive is refused by a destination with a renamed existing column. Both expose schema_mismatch. Complete readable application/authority/audit/transfer table rows and table definitions match before/after refusal. Cloudflare's protected _cf_ runtime metadata is excluded because D1 prohibits reading it.

The original full inventory, normalization, adoption, graph/reference validation and erasure assertions remain. No registration, assertion or workflow was removed or weakened. The repository's recorded test count stays 200/200; the matching inventory recount is 201 before and after because main has 22 browser entrypoints rather than the 21 in its last budget note. No test-budget change is made; COUNTS.json carries the inventory. Contract statuses and generated views remain untouched. No publication scan or DONE claim is made.
