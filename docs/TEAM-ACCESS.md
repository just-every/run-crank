# Native team access

The owner assigns explicit grants on Access. Each grant combines a product role with named workflows and accounts. Add another grant to retain an existing one, or replace the set deliberately. An empty set grants no product access. A Base sign-in role alone grants no product access.

One grant must cover the requested action, workflow and every account used by that action. A builder grant for a workflow cannot borrow account access from a viewer grant. Admins may delegate only actions covered by one of their own complete grants; an approver grant alongside an admin grant cannot supply missing delegation powers. They cannot change owner settings, issue credentials or administer another person's broader access.

Run-list payloads are checked against each workflow's complete read grant, regardless of grant order. Status-only grants never acquire customer values from a separate builder grant, including in legacy history and text or business-key searches. An explicitly empty search value still requires payload read authority; it cannot probe a status-only record.

Operators can preview and replay eligible failed steps in their scope. Completed effects stay complete and uncertain writes require reconciliation. Draft tests retain the initiating builder's authority revision, and publication retains its immutable execution authority. Removing access fences the next request and an admitted write before commit. Editor controls and approval availability check the complete grant for their own action and all accounts, even when a different role appears first.

Standing-grant reviewers receive only the proposed effects for tasks under the particular grant that names them; this confers no workflow-wide approval or payload access.

A starter cannot approve their own workflow run or legacy approval flow, including an owner. Rejection remains available to an otherwise authorized reviewer. A production-account draft test also needs a different native owner to confirm its exact effect.

Auditors read value-free audit history from their Account page. Billing administrators read monthly aggregate run counts and accounting units. These doors omit customer values, account credentials, workflow names and per-run details. Neither duty grants workflow or account access. A person assigned both duties sees both entry points on Account, regardless of grant order.

The one-time database upgrade snapshots existing non-owner access to existing workflows and accounts, with explicit action limits and a retained report available to the owner at `/api/crank/team/migration`. New people acquire no fallback permissions. An admin holding an explicit production workspace grant may delegate production creation within that grant. This grants only the recipient’s own new records, not the administrator’s records. An explicit production workspace grant permits creating production drafts and reading or preparing the records that person creates; it never grants another person's future records. Migrated administrators retain that creation privilege without gaining publication or draft execution. Adding an explicit grant preserves every existing migration action limit; submitted action limits cannot replace them. The append is fenced against the same recipient revision that was reviewed. Neither grants nor migration reports travel in a portable archive.

Folder records have stable installation identifiers and one environment. A grant may name `folder_ids` or `environment_ids` as well as exact workflows and connections. Folder grants cover descendants; environment grants cover records and creation within that environment. Each expansion stays inside its original grant. The older explicit `workspace:production` creation grant continues to cover only records created while that grant was current. Removing and regranting it does not reopen old records. Admin delegation checks the resource selectors as well as the role, actions and connections.

The owner manages resource records through `GET /api/crank/team-resources`, `POST /api/crank/team-resources/environments` and `POST /api/crank/team-resources/folders`. A workflow move uses `POST /api/crank/workflows/:id/move` with `folder_id`, or null for the environment root. Both source and destination require preparation rights and moves cannot cross environments. Direct draft edits cannot bypass this move door. Resource revisions fence late writes and old builder tests. Ordinary published work retains its immutable authority. Legacy approval flows also support scoped activation, pause and operator starts; the ownership-transfer door accepts either workflow kind.

Native provisioning uses SCIM 2.0 Users and Groups under `/scim/v2`. The native owner issues a one-time-shown credential through `POST /api/crank/team-provisioning/credentials`, assigning its immutable issuer URL. Only its hash is stored. It never authenticates at product doors. The issuing owner's current role and version remain live requirements. Revocation stops the credential and its group authority; an explicit replacement credential may resume that issuer without changing existing identities.

Identity is the issuer plus external id. Matching email addresses never merge people. Provisioning sends no invitation, creates no session and supplies no product grants. The owner maps a group's complete grants through `POST /api/crank/team-provisioning/groups/:id/grants`. Group creation uses environment or folder scopes; the legacy personal creation marker cannot be mapped to a group. Group updates are idempotent, support conditional ETags and fence current requests and draft-test continuation. Deactivation revokes native sessions and stored credentials; no owner can be deprovisioned. Operator erasure removes the provisioned profile and membership so the old external identity cannot reactivate the erased person.

Access grants, provisioning identities, group mappings, credentials and installation folder identifiers never travel in a portable archive. Folder labels remain metadata. Restored workflows are inactive and receiving access must be granted explicitly.

Standing-grant delegates and escalation recipients retain the exact source grant and immutable version. Their routing applies to that grant's runs, with current publication and grant checks repeated at approval commit. It cannot authorize a native run on a newer version. Explicit current approver grants remain separate.

TEAM-001 remains partial. Real Okta, Entra and Auth interoperability requires the owner's actual IdP tenant. Historical Base service-credential deactivation lacks an exposed native mint transport for a public-door fixture; current non-owner SCIM people cannot issue service accounts, and their native sessions are revoked through the tested transport.
