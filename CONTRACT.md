# Crank target contract

Target approved scope: **16 October 2026**. Category: **workflow automation (iPaaS)**. Crank is an owned Zapier/Make/Workato replacement: a connector library with managed OAuth credentials, webhooks/app events/polling/schedules, visual multi-step branching workflows with durable execution, AI agent steps and optional human approval where the action warrants it. It also targets the control and agent capabilities buyers seek in n8n, Gumloop and Pipedream.

The buyer connects the business’s applications so recurring work completes without copying data or supervising every step. Approval and idempotent HTTP delivery are one useful part of this whole job. This target replaces the old first-release exclusions of connectors, credential custody, schedules and live SaaS calls; it does not claim they already exist. No homepage, UI, manifest, code, test or workflow changes are authorized by this document.

Core records are workspaces, members/roles, connections and grants, workflows and immutable versions, steps/subflows/templates, trigger subscriptions/cursors, queues/runs/attempts, mapped inputs/outputs, remote effects, approvals, obligations, usage, import provenance, audit and erasure journals. All future capabilities below remain in scope even when marked missing. Each sibling remains its own product; Crank owns cross-app orchestration and integrates neighboring systems.

Acceptance journeys are repeated in [ACCEPTANCE.md](ACCEPTANCE.md). They run through UI, HTTP/CLI/SDK/MCP or provider doors, using fakes only at the network/paid edge in automated tests. A local edge test does not establish real provider consent, hosted operation, migration compatibility or customer acceptance. Live sandbox/provider journeys are required before a connector or migration can be called complete.

## Published clauses

### Workspace and HTTP delivery

#### WORK-001 — Visual multi-step workspace.

An operations lead creates, names, folders, searches, duplicates and connects workflows in a visual node-and-edge editor without code: steps are filled by picking account resources and fields by name (CONN-019) and routes are built with WORK-013 conditions, never by typing IDs or writing expressions. Each workflow has an owner, description, trigger, typed steps and enabled state; its graph shows branches, data lineage and validation errors. Every edge shows real sample data from WORK-014 step tests (recent records loaded from the connected account, the next real delivery, an earlier run, an action’s real response, or an explicitly labeled manual sample), with that sample’s source, so a builder sees what a field actually contains before mapping it. Draft edits and sample tests cannot send production actions unless explicitly authorized: a live action test needs its own WORK-014 confirmation naming the effect and account. Publishing a version is itself the authorization for that version’s declared steps on its bound connections (TEAM-004); limits and approval steps are opt-in.

**Acceptance evidence:** From the builder, connect a new lead trigger to a filter, CRM lookup, invoice draft and notification; test the trigger to load recent real leads from the connected test account and pick one, test each step and inspect the sample data and its named source at every edge, correct a missing required field, save and reopen the same graph, then publish it deliberately and observe its next triggered run complete with no further authorization step.

#### HTTP-001 — Authorized HTTP dispatch.

The existing custom HTTP connector delivers the immutable approved JSON body to the deployment-authorized exact origin, adds the run’s stable idempotency key, refuses redirects and binds success to the receiver’s returned effect ID and matching key. Failure or lost acknowledgment remains visible. One owner-controlled replay uses the same bytes/key; a compliant receiver records one effect. This connector’s manual mode remains available beside future standing-grant and app steps.

**Acceptance evidence:** Create and activate a flow through the HTTP API, prepare an event without sending, concurrently approve twice, lose the receiver acknowledgment, replay once and inspect one receiver effect; reject another run and refuse a foreign or credential-bearing destination.

### Run history and recovery

#### EXEC-004 — Replay any eligible step safely.

Operators retry/resume any eligible failed or incomplete step or selected batch items using retained versioned input and scoped authority. Preview shows what would run, prior effects and idempotency/reconciliation status. A corrected payload creates an attributable new revision; successful side effects are not silently repeated. Bulk replay has selection preview and limits. Until TEAM-001 adds an operator role, the owner replays. Eligible steps are the failed steps (and failed loop items) of a failed workflow run, plus failed loop items of a succeeded continue-on-error run, on a published, adopted workflow; a paused run resumes with run resume, an interrupted static read restarts by itself, and an interrupted or lost-response write is listed as uncertain with its operation key and goes to EXEC-006 reconciliation, never blind replay. Items that failed in a loop set to continue belong to a run that succeeded and whose later steps used its results; they are repaired with a linked new run on the same still-published version. The same digest-bound preview and selection limit apply; the source history stays unchanged. A repair retains completed checkpoints (including later steps), reopens only the selected failed items and their enclosing loops, and records `repair_of` and the selected paths. A path claimed by a repair is no longer eligible on its source, including concurrent decisions and after that repair is erased; the source retains the path claim until the source itself is erased; a failed repair is retried on that repair run. Unselected historical failures cannot be replayed through the copied checkpoints. The preview lists the eligible steps with their retained input, error, operation key and revision count, the uncertain writes and the completed effects that will not run again, and carries a digest; a replay names the selected paths (at most 100) and that digest, and a changed run refuses it. An uncorrected replay reuses the step’s retained input and operation key; a corrected input becomes revision N with operation key `<original>#rN`. Every revision keeps the replaced input, error and operation key beside the new input, with the owner and time, and the replay is audited with its paths and version. Completed steps and items keep their checkpoints and never run again; unselected failed items stay failed; each dispatch still checks live publish authority. Revisions are portable records under DATA-001 and erased with their run under DATA-002.

**Acceptance evidence:** Fail the fourth step after three committed effects, restart, preview and resume that step, then replay selected failed items with corrected data; verify the first three effects persist once and the original and corrected inputs remain distinguishable. Also finish a continue-on-error loop with two failed items and a successful later effect: preview and correct one failed item as a linked repair, verify the source history and later effect stay unchanged, the other item stays failed, concurrent decisions create only one repair, and its original and corrected inputs, operation identities, audit and restore links remain inspectable. Replay an uncorrected failed item and verify identical retained input and operation key.

#### EXEC-005 — Searchable run history and debugging.

Run history retains workflow/version, trigger provenance, original inputs, each step’s mapped inputs/outputs, timings, decisions, grants, attempts and remote object IDs under redaction and retention rules. Builders search/filter by workflow, business key, date, status and error, paginate beyond the latest page and compare prior runs. Incomplete executions remain available; UI distinguishes queued, rejected, failed, uncertain, `stopped by search`, `stopped by filter` and business-complete, and shows each filter and path group’s rule results.

**Acceptance evidence:** Find an older failed invoice by customer key, inspect its exact mapping and decisions, compare a passing run and follow the remote record link; deny a reader access to a restricted payload while retaining safe status/timing.

#### EXEC-006 — Effect reconciliation and compensation.

Every mutating step records intent, stable operation identity and known/unknown remote effects. Crank uses provider idempotency when supported, otherwise reads back by business key before retrying. Ambiguous matches stop for an accountable decision. WORK-011 find-or-create steps are mutating steps under this clause: a lost create is read back by its search key before any retry. Partial workflows can run explicitly authorized compensating actions; compensation has its own audit/outcome and never promises distributed exactly-once effects or reversal of an irreversible action.

**Delivered readback slice (c33):** A declared HTTP readback may name a bounded records list and exact business-key field. One exact match supplies the create-shaped result without another write; zero matches leave the write uncertain, and multiple matches require an accountable decision. Unavailable, malformed or incorrectly shaped readback never turns an unknown write into a replayable failure. Such uncertain writes remain ineligible for blind replay after restart. Native QuickBooks sandbox invoice and refund-receipt steps now use stable provider request IDs and readback by exact document number and customer. The owner may choose a current provider record with a digest-bound decision, then continue without repeating the original write. A separate published invoice-void workflow requires its own exact human approval, retains its own operation identity and outcome, and does not reverse payments or refunds. The held owner company grant and live US QuickBooks sandbox journey now prove invoice and refund creation, lost-acknowledgement recovery after restart, accountable continuation and separately approved invoice compensation. This proof does not complete CONN-007 or the broader business outcome under AGENT-001.

**Acceptance evidence:** Lose the response after an invoice/refund is created, restart and reconcile it by provider readback; simulate zero, one and multiple matches, then fail a downstream step and inspect an authorized compensation without duplicating the initial write.

### Approvals and data custody

#### TEAM-002 — Optional approvals and standing grants.

Approval is a configurable step or policy boundary, not a requirement for every run. A published workflow needs no grant to run: publishing authorizes exactly its declared steps on its bound connections (TEAM-004). Standing grants are opt-in limits layered on top, and they are the authority for agents, MCP clients and other work that is not a fixed published graph; they name workflow/version, app/account, tools/actions, fields, recipients, amount/rate limits and expiry. Routine actions proceed unattended within the publish authority and any grant. High-impact or out-of-policy actions show the exact proposed effect to an authorized human; rejection sends nothing, a change to the proposed action made by anyone but the reviewer invalidates the decision, and timeout/escalation/delegation are durable. Reviewers may correct a proposal before approving and choose where rejection leads under TEAM-005. Revocation stops new authority immediately.

**AI-003 receiver duty (ct scope-review-54):** A recurring task pins skill and objective versions; explicit adoption changes only the next run and leaves open runs frozen. A new version cannot widen grants without an owner grant under TEAM-002. Tool revocation blocks the next step dispatch. The first external send of a new version needs human approval unless a standing grant covers it, and the agent never approves. Standing grants retain AI-003's configured contact cadence, invoice billing-contact-only recipients and stops on paid/closed/void, takeover, cancellation, owner pause, authority expiry and budget hold; they do not bypass the live same-dispatch invoice read or contact operation identity. These are inherited obligations for the missing AI-003 capability, not additional delivered evidence for TEAM-002.

**Acceptance evidence:** Publish a routine lead workflow with no grant and observe unattended completion; give an agent task a limited grant and observe it complete within the grant; exceed a USD refund limit, inspect and reject one proposed action, approve another, then alter its body and revoke the grant mid-run, verifying reapproval/refusal and recorded in-flight uncertainty.

**Delivered semantics (ct ruling, 20 October 2026 11:50Z):** The native owner issues a separate, one-time-shown, hash-held execution credential bound to an immutable grant and the issuing owner's current identity/version; preparation credentials remain preparation-only. The owner chooses the workflow/version, each existing leaf tool and app/account, allowed top-level input fields (including their JSON subtrees), exact recipient paths/values, nonnegative USD amounts, per-tool rolling-minute admission limits, UTC expiry, native delegates and timeout/escalation recipients. Agents choose and order a subset of the declared tools, at most once per task, with literal inputs; transport, connections, retry/readback settings and source policy remain owner-declared. Each task retains an immutable graph and the source workflow's full owner-estimated per-run cost reservation; submitted values use the existing sealed/erasable run payload. USD bounds are inclusive exact decimal comparisons without rounding; the rate window is the preceding 60 seconds, one admission per tool invocation, with retries retaining that admission. Above-limit effects wait for a human decision on their exact input. A changed held proposal, including a deferred approved proposal, clears the old decision and retains the input revision and decision audit; no dispatched effect can be revised. The owner selects native delegates; after the owner-chosen timeout, a durable internal Approvals task opens to the escalation recipients without automatic approval or an external-delivery claim. Every step and physical request checks live grant/version/connection authority. Revocation fences leases and records already-started writes as uncertain, never as cancelled remote effects. Revoke a tool before the next step dispatch and verify refusal. Require a human decision for a new version's first external send unless a standing grant covers it, and deny agent approval. Verify the grant cannot bypass configured cadence, invoice billing-contact-only recipients, the same-dispatch connected-invoice read, operation-key deduplication or any AI-003 stop (paid/closed/void, takeover, cancellation, owner pause, expiry or budget hold).

#### TEAM-003 — Scoped preparation and trigger credentials.

Owners issue agent preparation/read credentials and one-flow trigger credentials stored only as hashes. An agent preparation/read credential is shown once at issuance and is reusable for preparation and read until revoked or until the owner’s identity or version changes; it never carries execution authority. Preparation authority cannot activate, approve, replay, manage data or escalate its own permissions. Revocation and owner identity/version changes invalidate credentials at the HTTP and transaction boundaries. Future execution tools receive separate explicit grants under TEAM-002.

**Acceptance evidence:** Issue both credential kinds through Access; verify the agent preparation/read credential is shown once at issuance, is not retrievable afterward, and only its hash is kept. Separately change the owner’s identity or version and verify credential invalidation; inspect state and archive for absence of bearer values.

#### TEAM-005 — Approve with edits, rejection routes and reviewer notices.

An approval step can mark fields the reviewer may edit (for example refund amount or email body). The reviewer sees the exact proposed action, edits allowed fields and approves the edited version; the edit is recorded as an attributable revision beside the original, re-validated against the mapping schema and any TEAM-004/TEAM-002 caps, and only the approved revision is sent. Builders choose whether rejection stops the run or continues down a named rejection branch carrying the reviewer’s reason. Reviewers are notified by email, Slack, Microsoft Teams or Nook and mobile push, each with an authenticated link; reminders and timeout routes follow the business calendar.

#### DATA-002 — Erasure, receipts and restoration fences.

Owners erase completed run data and related sensitive inputs, decisions, outputs, files, indexes and agent memory after stopping affected execution. ## Target clauses

### Build the automation

#### WORK-002 — Mapping, formatting and conditional routes.

Builders map nested fields and files between steps, validate against connector schemas, format US dates, timezones, USD amounts and decimals, transform text, numbers, dates and JSON with the WORK-012 built-in transforms, and choose filters and exclusive or parallel paths with the WORK-013 condition language. Missing, null and empty values stay distinct; invalid mappings name the field and prevent an unintended write. A public file URL mapped into a file input (for example a Typeform upload link) is fetched into a file reference with name, type and size under SEC-002 egress rules and the CONN-005 size and type bounds; a refused address, redirect into a private network, timeout, oversize or non-2xx response fails with the named error `file fetch failed` and no write.

**Line items.** Connector schemas mark line-item arrays (deal line items, order lines, invoice and bill lines, cart items), and an array maps to an array: one source with N lines produces one destination record with N lines, never only the first line and never one record per line unless the builder chooses a loop (WORK-003). Each line maps its own description, product/item reference, quantity, unit price, amount, discount, tax code or taxable flag and class/location where the destination has them. A **line-itemizer** transform builds line-item arrays when a source has none: from comma-separated or mapped values, by splitting a delimited field, or by zipping parallel lists (names, quantities, prices) into line objects, with unequal list lengths a named error. USD line amounts are exact decimal cents: line totals, discounts, tax and shipping reconcile to the source total to the cent, and a mismatch, a zero-line source or a line missing a required field routes to a named validation failure instead of writing a partial or empty record.

**Acceptance evidence:** Use the builder with a US lead containing nested addresses, a missing optional field and a USD amount; test both qualifying and filtered branches, a null value and invalid currency input, then inspect the exact mapped destination payload. Map a HubSpot deal with 3 line items (one discounted, one non-taxable) and a Square order with 4 lines into QuickBooks Online sandbox draft invoices: readback shows 3 and 4 lines with matching quantities, amounts and tax codes, and each invoice total equals its source total to the cent; build a 2-line invoice with a line-itemizer step from comma-separated sheet values; zip parallel lists of unequal length and verify a named error; send a zero-line source and verify a named validation failure and no invoice created. Map a Typeform file-upload URL into a Google Drive upload and verify the file by readback with its name, type and size; map a URL that redirects to a private-network address and verify `file fetch failed` with no request past the refusal and no write.

#### WORK-003 — Loops, joins and batch processing.

Workflows paginate source datasets, iterate records with bounded concurrency, aggregate results and merge streams by explicit keys and join policy. Per-item success and failure remain inspectable; resumption preserves completed items and does not repeat their effects. Ordering and empty-input behavior are declared.

**Acceptance evidence:** Run a paginated order batch through a loop and two branches, join by order ID, interrupt after some invoices are created and resume; inspect unmatched records and confirm each completed order retains one invoice.

#### WORK-004 — Durable delay and event waits.

Delay-until, interval waits and callback/event waits persist across restarts and deployments without holding a browser open. The owner sets timezone, expiry, business calendar and cancellation policy; late or duplicate callbacks do not resume a step twice. A **delay queue** step serializes runs through a named queue that any workflow in the workspace can share: each run waits until the queue’s previous item has been released plus a declared spacing, items release once each in arrival order, the queue survives restarts and deployments, and its depth, oldest item and next release time are visible. #### WORK-011 — Search steps: found, not found, several found, and find or create.

#### WORK-013 — Filter and path condition language.

Every filter step, every path rule, and every routing condition on a WORK-011 search outcome, a WORK-007 table lookup or an EXEC-003 error branch uses one condition language that a builder sets without code. Each rule names a mapped field, an operator and an operand (typed, picked or mapped from an earlier step), and the operator set is:

- **Text:** contains, exactly matches, is in a list (typed in the rule or mapped as a list), starts with, ends with and matches pattern (regular expression), each with its negation (does not contain, does not exactly match, is not in a list, does not start with, does not end with, does not match pattern). Text rules are case-insensitive by default with a per-rule case-sensitive switch, and leading and trailing whitespace is ignored unless the builder chooses otherwise.
- **Number and USD amount:** greater than, less than, equal to, not equal to, greater than or equal to and less than or equal to. Operands are parsed with the WORK-012 number and amount rules (so `$1,234.50`, `1234.5` and `100` are numbers) and compared as exact decimals, never as text: `100` is greater than `99`.
- **Date/time:** after, before, equals, on or after and on or before, comparing instants or, when the builder chooses day precision, calendar days. Both sides resolve in a declared IANA timezone (the workspace default unless set on the rule). Operands may be relative: now, today, start of this week or month, now plus or minus N minutes, hours, days, weeks or months, and plus or minus N business days on the WORK-004 business calendar.
- **Boolean:** is true and is false, accepting the field type’s declared true and false forms (true/false, yes/no, 1/0).
- **Existence:** exists and does not exist (the field is absent or null), and is empty and is not empty (present as an empty string, whitespace only or an empty list), keeping WORK-002’s distinction between missing, null and empty; the rule trace shows which of the three the value was.
- **Lists:** for an array field, any item matches or every item matches the inner rule, and list length compared as a number.

**Rule groups.** Rules combine with AND inside a group, and groups combine with OR. A filter or path rule allows at least 50 rules per group and 20 OR groups; the limits are stated in the editor and are never below these.

**Paths.** A path group holds at least 20 branches (Zapier allows 10) and nests at least 5 levels deep (Zapier allows 3). Each group is **exclusive**, running only the first matching branch in the declared order, or **parallel**, running every matching branch as its own branch of the same run with its own step history and an optional WORK-003 join. Each group may have one **fallback** branch, which runs only when no other branch matches, or one **always-run** branch, which runs whatever else matches, but not both. The editor warns before publish when a group has no fallback, and a run in which no branch matches and no fallback exists ends as `stopped by filter`.

**Type mismatches.** A value that cannot be read as the rule’s type (text in a number or USD rule, an unparseable date, a list in a boolean rule) produces the named outcome `type mismatch`, which names the rule, the field and the value. The builder chooses per filter or path group whether a type mismatch halts the run as a validation failure under EXEC-003 (the default) or routes to a declared branch. It is never a silent pass or fail.

**Preview.** Before saving, the editor shows each rule’s resolved operands and pass or fail, and each group’s and branch’s result, on the step’s WORK-014 samples, naming each sample’s source.

**Run history.** A run that a filter stops, or in which no path branch matches, ends with the non-error status `stopped by filter`. Run history (EXEC-005) shows the stopping group, each rule’s resolved operands and its result, and the status is filterable there, counted apart from failures in OPS-001, sends no EXEC-003 failure notice and does not count toward EXEC-003 auto-pause. Every path group in a run records which branch or branches ran and the rule results that chose them. The builder previews each rule’s result on the step’s sample data before saving.

**Migration.** MIG-002 maps every Zapier filter and path rule operator (text, number, date/time, boolean and exists rules), each AND/OR group, and each fallback and always-run branch to a committed operator here. MIG-003 maps every Make filter operator (text, numeric, date, time, array and boolean operators, their case-insensitive variants, matches pattern, exists and does not exist) and router fallback routes. MIG-001 maps n8n IF, Filter and Switch conditions (string, number, date, boolean, array and object operators, the AND/OR combinator, ignore case, loose type validation and the Switch fallback output). An operator with no committed equivalent is named as a manual conversion in the coverage report, never dropped.

#### CONN-002 — Managed OAuth, keys and connection lifecycle.

Owners authorize multiple accounts through provider OAuth or scoped API keys; Crank encrypts credentials under installation-controlled custody, refreshes tokens, rotates keys, tracks consent and permits team ownership transfer. #### CONN-011 — Custom, enterprise and private app connections: custom connectors, private gateways and pipelines.

Technical teams build versioned custom connectors from documented APIs/OpenAPI with typed inputs, pagination, OAuth/key declarations, webhook verification and reusable tests. PostgreSQL, MySQL, SQL Server, SFTP and S3-compatible data-pipeline recipes use typed connectors or reviewed custom connectors, authenticated customer-controlled private gateways and incremental checkpoints; large files stream with explicit bounds. Workato-class deployment includes environment separation and scoped service accounts.

**Private gateway rules (ct, 21 October 2026).** Only the owner enrolls a gateway, in a native browser session after the fresh email-link step-up within the preceding five minutes, with a single-use 256-bit enrollment code shown once, stored only as its SHA-256 hash, expiring after 15 minutes and naming one installation, one environment and the gateway. The gateway program generates an Ed25519 key pair on the customer host; Crank keeps only the public key and fingerprint. The gateway connects only outward to Crank over HTTPS, signs every request over method, path, body digest, timestamp and a single-use nonce, and accepts only installation-signed jobs. A gateway serves exactly one installation and one environment. It does nothing until the owner grants it one connector at an exact version, named operations and named private destinations; a new connector version needs a new grant, and every grant change bumps the TEAM-001 authority revision. Database, SFTP and storage credentials stay on the gateway host, referenced by name, and never reach Crank, run history, logs, audit or archives. Crank and the gateway each check status, environment, grant revision, connector version, operation and destination on every dispatch; the gateway runs only the granted version's typed operations against granted destinations after its own resolution, follows no redirect, always refuses link-local and metadata addresses and is never an arbitrary network proxy. Owners and admins revoke a gateway or grant without step-up, effective from the next dispatch; later results are withheld and the run fails with `gateway revoked`. A request for another environment's gateway, connection or secret is refused, audited and shown as a named access decision. A scoped service account is an owner-minted non-person credential bound to one environment and to workflow and connection scopes no wider than the owner's live authority, shown once, stored only as a hash, expiring (365 days by default, 730 at most), suspended when its authority ends and never transferred. SEC-003 audits codes, grants, revocations and refused dispatches without secrets or payloads; archives carry no code, gateway key or grant authority, so a restore brings gateways back revoked and grants inactive. #### TRIG-001 — Scoped, deduplicated webhook admission.

Every workflow can receive webhooks from senders that cannot add custom headers or wrap their payload. Each flow has one or more inbound URLs with an embedded random secret that the owner can revoke and rotate (old and new URLs overlap for a chosen window), plus optional header credentials (the existing scoped bearer trigger credential). Builders can require provider signature verification: HMAC-SHA256/SHA1 over the raw body or a signed timestamped payload with replay tolerance, with presets for Stripe, Shopify, Calendly, GitHub, Typeform and Twilio. The URL accepts POST, PUT and GET with JSON, form-encoded, multipart (with files) or raw bodies; a raw mode exposes the body text, headers and query string to mapping alongside the parsed fields. Deduplication uses a builder-chosen key path (for example `data.id` or a header) or, when the payload has no ID, a SHA-256 digest of the normalized body within a stated window (default 24 hours, configurable from 1 minute to 30 days). The response is configurable: an immediate status/body/headers, or a synchronous response produced by the workflow within a bounded timeout. Crank’s `{event_id,input}` envelope remains one supported mode: stable source event identity deduplicates equal payloads, rejects changed payloads under the same ID and respects an erased-event fence. No inbound credential can read workspace data, approve or activate work, and revocation takes effect at the server.

Secret-URL envelope identities are permanent within their workflow: the same canonical input returns its existing run (or held decision), and changed input under that ID is a conflict even after the ordinary body-digest window. Header delivery metadata does not change that identity. Query-only GET fallback identities hash the method and normalized query; other body fallback identities hash the normalized body and file contents. Ordinary identities become eligible again when their receipt time is at or before the current time minus the configured window; still-held items remain deduplicated until decided. Admission commits the identity, uploaded files and either its queued run or held item together, repeating current hook/version and erased-event authority inside that transaction. Interrupted admission leaves no accepted identity without durable work.

Owner erasure of a terminal multi-step run requires its workflow paused (`POST /api/crank/data/erase`, `workflow_run_id`, `confirm:"ERASE"`). An opaque event-key digest permanently fences its webhook redelivery, including after restart and portable restore. Erasure preserves the audit chronology with its run subject anonymized and sensitive detail removed; payload/decision copies in linked run, step, wait, attempt, hold and obligation rows are removed. This does not claim complete subject/operator/file erasure under DATA-002.

**Acceptance evidence:** Call the public trigger endpoint with an active flow key, resend the same event, change its payload, send to another flow and revoke the key; verify a single pending run, conflicts/refusals and no unauthorized reads. Send a form-encoded POST with no auth header and no event ID to a flow’s secret URL and verify exactly one run with the fields mapped; resend it inside the dedup window and verify no run; send it after the window and verify a new run; send a Stripe-signed event with a valid and then a tampered signature and verify one run and one refusal; send a GET with query parameters and a multipart POST with a file in raw mode and inspect headers, query and file as mapped data; configure a synchronous JSON response and verify the sender receives it; rotate the URL and verify the old URL stops after the overlap.

#### TRIG-005 — Flood protection for bursts of trigger events.

Each workflow has a burst threshold (default 100 new records in one poll, or 100 instant events in one minute; configurable from 1 to 10,000). When a poll or burst exceeds it, Crank creates no business effects for the excess: it holds the whole burst as one reviewable batch, notifies the workflow owner (EXEC-003 channels), and shows the count, source, sample records and estimated USD cost. The owner can run all, run selected items, or discard; held events stay deduplicated by source ID and retained until decided, with reminders and an optional owner-chosen expiry. Releases are attributable and partial releases leave the rest held. Activation backfill (TRIG-003) remains a separate explicit choice.

The current held-batch review door is `GET /api/crank/holds/:id`: source, item count, retained samples/items, decision attribution and USD estimate state are returned together. Before any release, the owner quotes all four per-run components (orchestration, connectors, models and executors), including explicit zero quotes where applicable, with assumptions through `POST /api/crank/holds/:id/estimate`. Amounts are nonnegative USD decimals with at most eight decimal places; components sum exactly, multiply by the batch or selected item count, and round half-up to cents once. Estimates are labeled **owner estimate; not provider-verified**, as in TRIG-002. Missing pricing is labeled **cost estimate required** and releases stay blocked; no provider charge or zero is invented. OPS-002 separately owns measured usage, forecasts and spending controls.

A release supplies the reviewed `estimate_fingerprint`, binding the quoted assumptions and owner/time to the current published version and all remaining held source IDs and payload digests. New items, payload changes, a partial decision or version replacement require a fresh review. The owner may discard without a quote. A release commits its attributable decision and durable queued runs atomically; interruption before that commit leaves all selected items held, while executor loss afterwards leaves queued runs that resume once. Email is the current owner-notice channel; each notice channel added under EXEC-003 and CONN-004 inherits held-batch notices before shipping.

#### TRIG-007 — Feed and URL polling triggers.

Two built-in triggers start runs when something new appears at a URL with no app connector. The **feed trigger** watches one or several RSS 2.0, Atom or JSON Feed URLs and starts one run per new item, deduplicated by GUID/id, falling back to the link, then to a digest of title and date; a re-published or edited item with the same identity starts no run, and an item’s title, link, summary, content, author, categories, dates and enclosures are mappable, with the source feed named when several feeds share a trigger. The **URL poll trigger** sends a GET (with mapped headers and query parameters, and authentication from a stored connection under HTTP-002 rules) to any endpoint and reads a JSON array at a chosen path, or XML/HTML items selected by XPath; the builder chooses the dedup key path (`id` by default, or any path such as `data.ref`, or a digest of the whole item), and cursor, page or link-header pagination is followed. Both triggers use TRIG-004 intervals (1-minute floor) and latency reporting, TRIG-003 activation backfill (start from now, or process existing items) and TRIG-005 flood holds; requests obey SEC-002 egress rules, so private-network, link-local and metadata addresses and redirects into them are refused, response size and parse time are bounded, and fetch, parse and auth failures are visible on the trigger with EXEC-003 notices rather than silent skips. A URL poll’s header and query values are literal text or map `{{poll.since}}` (the start of the last successful poll, ISO 8601 UTC), `{{poll.now}}` (this poll’s start) and `{{poll.interval_minutes}}`; any other mapping is refused when the workflow is saved, and a value that maps to nothing is left out, so the first poll sends no `since`. Parse time is bounded by bounding the work, because a Worker’s clock does not advance during synchronous parsing: each response is at most 2 MiB, an XML or HTML document at most 200,000 nodes, and a poll at most 10 pages; exceeding a bound is a visible trigger error with the owner notice.

#### TRIG-008 — Updated-record triggers on watched fields.

Every “updated” or “changed” trigger defines what counts as an update: in every native connector (CONN-003 to CONN-018, including CONN-005 Sheets, Excel and Airtable rows and SharePoint list items, CONN-006 leads, contacts, companies and deals, CONN-007 invoices (status, balance, due date) and customers or contacts, CONN-008 Shopify orders, customers, products and inventory levels and Stripe subscriptions and customers, CONN-009 Zendesk tickets and Jira issues, CONN-014 work items, CONN-015 subscribers, contacts, opportunities and deals, and CONN-018 orders, payments and disputes), every CONN-010 Run Edit Run product trigger, every CONN-011 custom connector trigger and WORK-007 table triggers.

- **Watched fields:** the builder chooses one or more watched fields (sheet or Excel columns, Airtable and table fields, CRM object and custom properties, a pipeline and its stage, an order, payment, fulfillment or dispute status, an inventory level, a ticket’s priority or an issue’s status) with CONN-019 pickers, or explicitly chooses **any field**. A new update trigger cannot publish without that choice, and choosing any field shows a warning that every edit starts a run. A run starts once per change to a watched field’s value; edits to unwatched fields start nothing and count as nothing.
- **Changed to and changed from:** optionally, the value or set of values a watched field must change to (stage = Closed Won, Status in {Approved}), and optionally the value it must change from, set with WORK-013 operators. A change to any other value starts nothing.
- **Change payload:** each run carries, as mappable data, the record ID, which watched fields changed, each watched field’s previous and current value, and the change time: the provider’s modified or property-history timestamp where supplied, otherwise the detecting poll’s time, labeled as such.
- **Detection:** where the provider sends property-change events or keeps property history (HubSpot property-change subscriptions and property history, Salesforce Change Data Capture and field history, Pipedrive webhooks with previous values, Zendesk ticket event webhooks and Jira issue changelogs), Crank uses them. Shopify, Stripe, Square, PayPal and WooCommerce webhooks say which record changed and carry its current state, so Crank compares them against the snapshot below. Where it does not (Google Sheets, Excel, Airtable without a last-modified field, QuickBooks Online and Xero change notifications, which name the changed record but not its previous values, polled lists and items), Crank keeps a per-record snapshot of the watched fields only and compares on each TRIG-004 poll, starting runs only for differences. Activation seeds the snapshot from current values under the TRIG-003 backfill choice, so existing values start no run unless the owner chose backfill. Snapshots are workspace data under DATA-003 retention and DATA-002 erasure, and are re-seeded with no runs when a new version changes the watched fields.
- **Dedup identity:** by default record + field + new value + change time, so a Status that goes Approved → Pending → Approved runs again on the second Approved. The builder may instead choose **first time this value is seen** (record + field + value), Zapier’s trigger-column behavior, under which a value already seen for that record never runs again. Repeated or out-of-order deliveries of one change start one run (TRIG-003), and several watched fields changing in one edit start one run that lists every changed field.
- **Partial entry:** Sheets and Excel row triggers offer an optional **settle delay** (1 to 60 minutes): a new or changed row runs only once its watched and mapped columns have stayed unchanged for the delay, with the values at release, so a row typed cell by cell is not sent half filled. An optional “required columns filled” condition holds a row until those columns are non-empty.
- **Migration:** MIG-002 maps Zapier’s trigger column (and “any column”), each Property Change trigger’s property, and Updated Deal Stage’s pipeline and stage onto watched fields and changed-to values, using the first-time-seen identity where the source used a trigger column. MIG-003 maps Make watch modules’ field and “changed” options, and MIG-001 maps n8n trigger options such as the Google Sheets Trigger’s columns to watch. Any other update setting is a named manual conversion, never a silent widening to any field.

### Operate recurring work

#### EXEC-001 — Durable queues and execution checkpoints.

Activated workflows execute without a person per run under published authority and any applicable grants. Durable queues show queued/running/waiting/dead-letter states, depth, oldest age, priority and owner. Atomic claims, per-step checkpoints, concurrency limits and cancellation survive executor loss and deployment; lease expiry records uncertainty before recovery. Pausing states whether it stops intake, dispatch or both, and cancellation identifies already-started effects.

Execution priority is an integer from -100 to 100 (default 0), higher first, then receipt time and stable run ID. Each admitted version freezes `max_concurrency` (1–100, default 1); its claim counts every unexpired running lease of the same workflow across versions. Waiting, approval and paused runs occupy no execution slot. A saturated workflow is filtered before the scheduler’s candidate limit.

The Operations live inventory is independent of historical date bounds and respects its workflow/team filters; depth counts the complete inventory, with the first 100 runs shown by execution order. Dead letters are retained terminal failed runs (including uncertain writes), with their checkpoints and error category, and never dispatch automatically. An expired lease atomically marks in-flight mutating checkpoints uncertain before recovery. Cancellation fences the lease and all later dispatch, preserves completed checkpoints, and labels an already-started write uncertain because it may still complete; it does not undo effects. Paused workflows hold new trigger intake and refuse on-demand starts. #### EXEC-002 — Rate limits, backoff and exhaustion.

Connector workflow execution distinguishes proven-not-sent/transient failures from uncertain effects and permanent errors. Retries honor Retry-After, exponential backoff with jitter, provider/account rate limits, concurrency and attempt/time budgets. Exhausted work stays durable with its next owner action; throttling one account does not starve another. Outside runs, trigger polling/historical fetch (TRIG-003/004/007), connection consent/test/token lifecycle (CONN-002) and operational log delivery (OPS-001) retain their own lifecycle policies.

All shipped workflow request operations conform: general HTTP, public file downloads and native Slack, including pagination and readback. Safe reads default to 6 attempts: backoff is 60 seconds × 2^(completed attempts − 1) plus uniform 0–250 ms jitter, saturating at one hour. A step may explicitly set `retry_policy.read_attempts` (1–10) and `retry_policy.base_delay_ms` (1–3,600,000). Retry-After (delta seconds or HTTP date) is a lower bound; an absent/invalid header uses backoff. A provider-required wait beyond one hour durably exhausts instead of sending early. HTTP 429/502/503/504 and transient network failures retry safe reads; permanent auth errors stop. Slack POST reads declare read safety in their request identity. A mutating HTTP request makes at most 2 attempts only after a lost response with an explicit provider idempotency header; its default backoff starts at 500 ms plus the same jitter. Slack writes make one attempt. A lost write without that guarantee resumes its declared readback or remains uncertain, never blind replay. Multipart retries retain identical bytes, MIME boundary and operation key across restart.

Each request has a 60-second active wall-clock budget per execution slice. Waits of 30 seconds or less sleep in-request within that budget. Longer waits persist the exact input, immutable version, operation identity, completed-response checkpoints, original request budget identity and attempt count, park the run, and release its workflow execution slot. The first Cron tick at or after due queues it, rounding the wait up by less than one minute; workflow concurrency may delay actual execution further. History distinguishes earliest scheduled retry, Cron release and actual resume. A recorded park starts a fresh active slice on actual resume; restart without a park retains its original slice deadline. Every resumed dispatch still checks current publish authority and connections. Each actual parked interval, including Cron rounding and capacity delay, is capped at one hour; intervals are summed across the run's requests with a 24-hour total cap. Crossing either cap durably exhausts with the budget reason and next owner action. Parked runs count toward workflow concurrency only while executing.

Private, bounded completed-response checkpoints stored in 64 KiB chunks reconstruct earlier pages without refetching changed records and resume a lost write's readback phase without repeating the write. They exclude credential headers and credential query URLs, keep the existing 2 MiB HTTP, 1 MiB file and 4 MiB Slack response bounds, participate in subject-erasure review, and are deleted atomically when their step/run settles or is erased. They are portable under DATA-001 and restore inactive without receiving authority. Request identity remains a value-free digest. Retry parameters are frozen on each published/test version; existing immutable versions keep their prior defaults, and rollback retains the restored version's parameters.

Requests enforce the catalog default of 100 requests per 10-second half-open rolling window and 4 simultaneous requests per connection. Unconnected requests share an origin bucket. Retries, pagination, file downloads and readback consume the same capacity. Completed admissions remain counted for the full window after their response, so slow requests cannot create a later burst; abandoned concurrency leases expire after the bounded request deadline plus 2 seconds. Transient value-free admissions are not portable authority. CONN-002 inherits shared-account buckets when provider-verified account identity exists. CONN-003–019, HTTP-002, EXEC-007, WORK-005, AI-001 and PLATFORM-002 inherit this clause for each added workflow request capability before it ships.

- **What expires:** payload expiry clears a finished run's trigger data, response, step input, output and trace, step-revision inputs, wait proposals and decisions, held and historical event copies and resumable request responses, and reduces each failure to its category; the run, its step statuses, times, business key, source event id, audit and a value-free receipt stay, and the run can no longer be replayed. History expiry removes the whole run through DATA-002's erasure (event-digest fence, value-free receipt carrying its workflow, outcome and cutoff). Every expiry advances the portability redaction checkpoint and file deletions fence their rows, so an archive made before the expiry is refused against this installation or a later archive supplied as the journal (`erasure_epoch`).
- **Always kept:** unfinished runs, runs waiting for a decision, runs with an unverified business obligation (OPS-001), runs with an uncertain write to reconcile (EXEC-006), runs with a repair in progress (EXEC-004) and held runs never expire; the dry run lists each with its reason.
- **Dry run:** shows, for the chosen periods, every run and file the maintenance pass would remove now (or as of a chosen time) and every kept run with its reason, and deletes nothing.
- **Legal holds:** the owner holds one exact identifier (3 to 500 characters, matched case-insensitively the way DATA-002 matches a subject) or one whole workflow, with a reason. A held run never expires and its DATA-002 erasure is refused (409) until the owner releases the hold; release keeps the hold's record and digest and removes the identifier. Placing and releasing are audited.
- **Disclosure:** the Data screen states the defaults, the periods, the cleanup that already runs on its own (request-rate admission windows after their window, a paused workflow's held events at the expiry chosen for that hold, resumable request responses when their step finishes) and that run lists page the newest runs while older runs are kept.
- **Sensitive data:** the owner sets each workflow's data class (none, customer, financial or health). A financial or health workflow publishes or resumes only while the owner's attestation for that class is recorded, naming each provider agreement in place (for example a BAA) and where the data is held; it is labelled owner-attested and Crank never claims to have verified or certified it. Withdrawing an attestation pauses every published workflow of that class at once.
- **Scoped encryption (ct 19 Oct 17:20Z and 17:42Z):** Crank itself encrypts every payload value of a customer, financial or health workflow: trigger data, the webhook response, step input, output, trace and failure detail, replay and repair inputs, approval proposals and decisions, held and historical event copies, and run files. Each value is AES-256-GCM ciphertext under the installation's key for that data class, bound to its workflow and key; beside it stay only value-free routing facts (the file ids it names, an HTTP step's method, a failure's category, code, HTTP status and uncertainty, retry ids and times). Each installation makes its own random key per class on first use and seals it under the installation secret, like connection credentials; the blind-index HMAC-SHA-256 key is derived from the same key. Values are sealed on write; the per-minute Cron pass brings at most 25 runs, 50 held or historical copies and 10 files a minute to their workflow's current form, each run in one atomic batch that a concurrent write or execution defers: this migrates existing payloads when a workflow is classified, re-seals them on rotation and returns them to plaintext when a workflow leaves both classes. The owner rotates a class key at once (typed ROTATE); new values use the new key, the pass re-seals and re-indexes everything, and the old key is destroyed (its material deleted, the event audited) once no value, digest or run refers to it and 15 minutes have passed since it retired. Key creation, rotation, destruction, export and import are audited. Customer data needs no attestation; financial and health data also need the attestation above.
- **Blind index:** the owner declares a sealed workflow's identifier fields (up to 20 property names). Their text or number values, trimmed and lower-cased, found at any depth of the trigger, step input or step output, are kept only as HMAC-SHA-256 digests under the class key. DATA-002 subject erasure and subject legal holds match a sealed run by its business key or when the identifier exactly equals one of those values; free text inside sealed values is never matched, and run search says that text search does not reach encrypted payloads. While any run waits for the pass to seal or re-index it, or is sealed under a key this installation does not hold, the subject preview names that and erasure waits. Payload expiry deletes a run's digests with its values; run erasure deletes them with the run.
- **Archives and keys:** keys never travel in an archive; an archive carries the ciphertext and digests. After a fresh email-link confirmation (step-up), the owner downloads a key file holding every key not yet destroyed, wrapped with AES-256-GCM under a key derived from the owner's passphrase (12 to 500 characters; PBKDF2-SHA-256, 100,000 iterations). Restored on another installation without it, runs, outcomes and audit restore and each sealed value shows as sealed and labelled; after its own step-up, that installation's owner imports the key file with the passphrase, the values read again, and its pass re-seals them under that installation's own key and then destroys the imported one.
- **Later capabilities:** AI-001, AI-003, AGENT-001 to AGENT-004 (model context and agent memory), WORK-007 (tables and forms), WORK-009 (collected answers), WORK-010 (digest entries), TRIG-006 (inbound email) and EXEC-007 (sent messages) store payload values and must seal them for customer, financial and health workflows under these rules before they ship.
